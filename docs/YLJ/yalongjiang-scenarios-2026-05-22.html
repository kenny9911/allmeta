为何AI · 5 根支柱

为何必须是 AI & 多智能体调度 — 老软件解不动的 5 个结构性原因

客户 & Pod 内训共用口径
01

多目标冲突

发电效益 × 弃水弃风 × 电网考核 × 安全约束 无单一最优解; 调度长的经验必须被编码成约束与偏好, 不是简单的线性规划。

02

多时间尺度

从 T-72h 中期预测 到 T-0 执行复盘, 每个窗口由专属 Agent 负责; 单一模型在所有尺度上都最差。

03

多源异构

气象 / 水文 / 电网 / 设备 / 市场 / 政策 数据形态完全不一致; LLM 是把 PDF / 表 / 时序揉成统一语义的最便宜手段。

04

多部门协同

调度 / 营销 / 集控 / 新能源 / 电厂一线 五条线口径不一; Agent + Ontology 才能把跨部门口径统一到同一事件链。

05

高度不确定

来水 / 天气 / 市场全是概率分布, 不是点估计; 必须 可重放 + Human-in-loop + Reflection, 才能合规、可审计、可对赌。

1
短临 + 中期气象预测
T-72h · 0–6h / 24–168h
Agents
气象预测 Agent
LLM / AI 能力
盘古气象大模型 + 流域微气象订正; 集合预报给出概率带, 而非单点值。
老软件做不到 · 数值天气模式 (NWP) 对流域级微气象失真, 需 LLM 融合多模态实测做订正。
2
来水预测 + 不确定性
T-72h → T-48h
Agents
水库来水 Agent
LLM / AI 能力
分位数 / 集合预报; 水库 / 流域多尺度建模, 输出含不确定性带的来水曲线。
老软件做不到 · 经典水文模型只给点估计, 不带概率; 调度无法做风险定价与情景对冲。
3
设备健康 + 检修排程
T-48h · 容量刷新
Agents
设备健康度 Agent
LLM / AI 能力
机组诊断 + 检修窗口推演; 把可用容量与检修窗口耦合, 影响下游调度边界。
老软件做不到 · 现有检修系统只是台账, 不会算 "检修窗口 × 来水 × 电价" 的机会成本。
4
水电调度候选
T-24h · 候选窗口
Agents
水电调度 Agent
LLM / AI 能力
多档发电曲线生成 + 含上下游联调; 一次给出 N 套候选, 供顶层 Orchestrator 决策。
老软件做不到 · 传统软件输出单一计划解, 而业务必须看 N 种可能性才能决策。
5
风光协同消纳
T-24h · 候选窗口
Agents
风光协同 Agent
LLM / AI 能力
出力曲线 + 弃风弃光评估; 与水电的调节容量协同, 在候选阶段已考虑消纳约束。
老软件做不到 · 风光场站 SCADA 与水电调度是孤岛, 联合优化必须靠跨域 Agent + Ontology。
6
多目标联合调度 ⚡
T-12h · 顶层优化
Agents
⚡ 智慧运行总编排
LLM / AI 能力
多目标优化: 发电效益 × 弃水弃风 × 电网考核 × 安全约束; 把调度长经验编码为偏好。
老软件做不到 · 多目标冲突无单一最优, 经典 OR 也调不出含隐性偏好的方案。
7
应急响应
T-6h · 压力测试
Agents
应急响应 Agent ⊙ 调度长 Human-in-loop
LLM / AI 能力
极端情景压力测试: 汛期 / 特枯 / 暴增 / 弃风; 调度长在关键节点强制介入与微调。
老软件做不到 · 应急预案是 PDF, 不会"被执行"; Agent 在事件触发时主动跑预案。
8
闭环复盘 + 校准
T-0 → 下一轮
Agents
Reflection Agent
LLM / AI 能力
实绩 vs 预测偏差归因; 校准每个 Agent 的 Evaluation Metric, 反馈下一轮预测。
老软件做不到 · 复盘报告是事后总结, 不会反馈回算法; Reflection 把复盘变成工程闭环。
