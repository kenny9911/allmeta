# Agentic 发电计划 · allmeta 同构重写 · 2026-05-22

> 配套 HTML 投屏稿: [[yalongjiang-plan-2026-05-22.html]]
> 上下文: 国际中软在客户处展示的「基于智能体集成中枢的发电计划生成逻辑」 (见上 `Pasted image 20260522110338.png`). 本笔记把那张图按 allmeta 架构同构重写一遍, 作为雅砻江战略研讨的第三张图.

## 一、核心转化 · One-Line Shift

图中本质上是一棵函数调用树: Master Agent 拆任务, 4 个 Slave Agent 各自调技能, 结果汇总返回. 这是把传统 SOA 用 Agent 重画了一遍.

**allmeta 把这棵树拍平成一张事件网**:

- 业务语义由 **allmeta Ontology** 统一定义 (电站 / 机组 / 检修单 / 出清结果 / 计划版本 都是 Entity, 不是 RPC payload)
- 调度由 **Agentic Operator 事件总线** 驱动 (Agent 之间无函数调用栈, 订阅事件类型)
- 安全隔离从「网络黑盒」升格为「Ontology 镜像 + 事件队列」, 跨区可审计

这正是 [[yalongjiang-scenarios-2026-05-22.html]] 里讲过的「为何AI 5 根支柱」第 03 / 04 条 (多源异构 / 多部门协同) 的实施层答案.

## 二、1:1 组件映射

| 国际中软原图 | allmeta 实现 | 关键差异 |
|---|---|---|
| 代理网关 (RPC 转发) | **Ontology API 门面** (GraphQL/REST) | 「提交需求清单」= 一次 Ontology 查询, schema 即契约 |
| 安全隔离设备 (网络层防火墙) | **Ontology 镜像 + 事件队列** | III 区只见 IV 区的只读语义投影; 写入显式排队, 语义级审计 |
| Master Agent (任务分解) | **Plan Conductor Agent** (Agentic Operator 内一个角色) | 不是「主」, 只承担「日前计划编排」; 应急 / 复盘可挂不同 Conductor |
| Slave Agent 1-4 (硬编码 4 个) | **Capability 注册 + AgentGen 派生** | 哪个 Agent 处理 `maintenance.schedule` 由 Ontology 决定, 不是 Master 内 switch-case |
| 8 个技能工具 (8 个 SDK) | **Ontology Capability + Tool Adapter** | 统一 Action 类型, 一份 Adapter 接口, 不是 8 套客户端代码 |
| 智能体 · 径流 / 功率 / 交易决策 | **Specialist Agents · Conductor 的 peer** | 不是 child, 是 peer; 任何一个都能编排其他 |
| 日前/日内发电计划 Agent (JSON payload) | **PlanCompose Agent + PlanVersion Entity** | 计划本身是 Ontology Entity, 有版本 / 血缘 / 署名 |
| 流程编号 1-8 (RPC 时序) | **8 类事件 (`*.Required` / `*.Produced` / `*.Published`)** | 每步可重放 · 可人在回路 · 失败有 retry/DLQ |

## 三、8 步流程在 allmeta 下的重排

图中 8 步是 RPC 时序; 重排后是 8 类事件:

1. `PlanRequest.Submitted` — 客户提交需求清单 (= Ontology 查询模板), Conductor 订阅
2. ~~请求转发~~ → Conductor 解析后**发布**子任务事件 (`Forecast.Required`, `Maintenance.Required`, `Clearing.Required` …)
3. ~~指令下发~~ → 跨区写入 = 在 III 区**入队**事件, IV 区 mirror 消费 (有审计)
4. ~~任务分解智能体~~ → 已经存在: 任何订阅 `*.Required` 的 Agent 自行认领 (capability match)
5. ~~调度指令~~ → 等价于事件总线的 fan-out; 不是 Master → Slave, 是 topic → subscribers
6. 子任务 Agent 产出 `*.Produced` 事件 (径流 / 功率 / 出清 / 检修窗口都是 Ontology Entity, 不是 dict)
7. ~~结果解析~~ → PlanCompose Agent 订阅所有 `*.Produced`, 满足前置条件后**写出** Plan v_N
8. `Plan.Published` 事件 — 下游 (AGC、营销、复盘) 各自订阅; 全链路可重放

**关键**: 没有「返回」. 没有 caller 等待 callee. 任何一步可被 replay、重新评估、人在回路审批 — 这是图中那种 RPC 时序结构里做不到的.

## 四、Ontology 必须长出的节点

```
Entities:    PowerStation · Unit · MaintenanceWindow · PlanVersion ·
             ClearingResult · ForecastRun(径流|功率|电价) · AGCSetpoint ·
             PolicyDoc · MarketSnapshot

Relations:   Plan -derives_from-> ForecastRun
             Plan -respects-> MaintenanceWindow
             Plan -optimizes_against-> ClearingResult
             Unit -has_state-> EquipmentHealth
             Plan -supersedes-> Plan(v_N-1)
             ForecastRun -uses-> Weather / Hydro / Market

Events:      *.Required / *.Produced / *.Published /
             *.Approved / *.Stale / *.Replayed /
             Incident.Triggered / Incident.Resolved

Capabilities (Agent 注册声明, 替代「Slave 1-4」硬编码):
             forecast.runoff       · MAE
             forecast.power        · MAE
             forecast.price        · P&L
             clearing.bid          · 出清盈亏
             maintenance.schedule  · 冲突率
             plan.compose          · 目标偏离
             review.attribution
```

这套 Ontology **不是为发电计划一个场景写的** — 对 [[yalongjiang-scenarios-2026-05-22.html]] 里那 8 个场景全部复用. 这就是 RAAS 同构参照要传达的 *Same Backbone · Different Ontology*.

## 五、相对原图的 4 个架构升级 (卖点话术)

1. **不固定 Master/Slave 树形 · 谁来编排可换** — 日前计划用 PlanCompose, 应急用 IncidentConductor, 复盘用 Reflection. 同骨架, 不同 Conductor.
2. **跨区隔离 = 语义层而非网络层** — III/IV 区都见同一份 Ontology schema, 镜像 + 事件队列把写入显式化, 比「红色隔离设备」可审计得多.
3. **每 Agent 独立评估指标** — `forecast.runoff` 的 MAE / `clearing.bid` 的 P&L / `maintenance.schedule` 的窗口冲突率, 持续校准, 不是一锤子上线.
4. **可重放 + 人在回路** — 8 步是事件不是函数; 任何一步可暂停、改、replay. 这是政府 / 电网合规审计能接受的唯一形态.
